# 台式机主机平台建模依据

参考配置为 MSI MAG B650 TOMAHAWK WIFI、AMD Ryzen 9 7950X、两条 16 GB DDR5-5200 UDIMM，以及装在 `M2_1` 的 Samsung 990 PRO 2 TB 裸盘。软件示例使用 Linux v6.12 的 PCIe NVMe 驱动，演示单笔成功完成的 4 KiB 直接 I/O。规格和公开外观可对应实物，依照片推算的部件位置标为近似，封装内部功能块、物理地址到 DRAM 的分布和动画时间使用示意值。

## Ryzen 9 7950X、缓存与 I/O 裸片

- **封装。** 7950X 为 Raphael AM5 台式机 CPU，采用可拆卸的 1718 触点 LGA 连接和带顶盖封装。共 16 个 Zen 4 核心和 32 个线程。封装有两颗 5 nm CCD（每颗 71 mm²）和一颗 6 nm IOD（122 mm²）。AMD GDC24 的封装小图可作裸片相对位置参考，面积可用于约束比例。IHS 下的真实裸片宽高、精确姿态、底部触点分布、凸点布线和硅内布局留作独立机械或显微证据。[AMD 7950X 规格](https://www.amd.com/en/products/processors/desktops/ryzen/7000-series/amd-ryzen-9-7950x.html) · [AMD AM5 发布资料](https://www.amd.com/en/newsroom/press-releases/2022-5-22-amd-showcases-industry-leading-gaming-commercial-.html) · [AMD GDC24 第 12 页](https://gpuopen.com/download/GDC2024_AMD_Ryzen_Processor_Software_Optimization.pdf#page=12)
- **CCD 与缓存。** 每颗 CCD 含 8 核，核心各有 32 KiB L1I、32 KiB L1D 和 1 MiB L2，8 核共享同 CCD 的 32 MiB L3。主机线程经 CPU 缓存层次访问用户缓冲区、队列和驱动状态。DMA 的逻辑路径经 IOD 进入主机一致性域，队列及缓冲区的最新内容何时落到 DRAM、某次请求由哪一级缓存响应，取决于实际一致性和内存控制行为。可视化可表示访问、可见性和所有权的变化。[AMD GDC24 第 12、15 页](https://gpuopen.com/download/GDC2024_AMD_Ryzen_Processor_Software_Optimization.pdf#page=12) · [Linux DMA API 的一致性与映射类型](https://docs.kernel.org/6.12/core-api/dma-api-howto.html#types-of-dma-mappings)
- **IOD 与主板。** AMD 的 Raphael 图把 CCD、统一内存控制器 UMC、IO Hub、RDNA 2 与媒体模块接到 IOD 的 Data Fabric。UMC 连两条 DDR5 通道，主槽根端口在示意中归入 IO Hub。CPU 的原生能力为 PCIe 5.0、28 条总通道、24 条可用通道，此板 `M2_1` 与 SSD 的规格均为 PCIe 4.0 ×4。`M2_3` 经外置 B650 芯片组。IOMMU 画在 I/O 进入内存的逻辑路径上。其确切硅上位置、端口编号、BIOS 开关和运行时域配置需要另行实测或读取系统枚举。[AMD 7950X 规格](https://www.amd.com/en/products/processors/desktops/ryzen/7000-series/amd-ryzen-9-7950x.html) · [AMD Raphael 功能图](https://gpuopen.com/download/GDC2024_AMD_Ryzen_Processor_Software_Optimization.pdf#page=12) · [微星插槽规格](https://www.msi.com/Motherboard/MAG-B650-TOMAHAWK-WIFI/Specification) · [AMD IOMMU 规范 48882](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/specifications/48882_IOMMU.pdf)

## DDR5 UDIMM、bank 与 1T1C 单元

- **插槽与通道。** 从 CPU 向外为 `DIMMA1`、`DIMMA2`、`DIMMB1`、`DIMMB2`。双条样例装入 A2/B2，每个 CPU 内存通道一条。7950X 规格给出两条 1R 或 2R UDIMM 的 DDR5-5200 档。以每条非 ECC UDIMM 的 64 位数据宽度估算，两个 CPU 通道的理论合计带宽为 83.2 GB/s，即 `5200 MT/s × 128 bit ÷ 8`。实际速率由系统配置和训练结果决定。[微星手册第 28 页](https://download.msi.com/archive/mnu_exe/mb/MAGB650TOMAHAWKWIFI.pdf#page=30) · [AMD 7950X 内存规格](https://www.amd.com/en/products/processors/desktops/ryzen/7000-series/amd-ryzen-9-7950x.html) · [Micron DDR5 客户端模组白皮书](https://assets.micron.com/adobe/assets/urn%3Aaaid%3Aaem%3A5902f17e-8bde-4246-971c-8d7f274c6b1a/original/as/ddr5-key-module-features-wp-client.pdf)
- **模组例件。** Kingston ValueRAM `KVR52U42BS8-16` 给出 16 GB、DDR5-5200、1Rx8、非 ECC、288 针、八颗 `2G × 8` FBGA、JEDEC SPD 42-42-42 与 VDD/VDDQ 1.1 V。PCB 标称长 133.35 mm、高 31.25 mm。每条 UDIMM 有两个独立 ×32 子通道，每个子通道由四颗 ×8 器件并行组成。用金手指、定位缺口、两组 DRAM 封装、PMIC、SPD Hub 将模组拆成可选部件。每个 ×32 子通道一次 BL16 的负载为 64 B。颗粒内的 on-die ECC 属于器件内部功能，模组的主机数据接口仍以非 ECC 例件为准。[Kingston 规格和机械图](https://www.kingston.com/datasheets/KVR52U42BS8-16.pdf) · [Kingston 模组规格](https://www.kingston.com/en/memory/search/discontinuedmodels?partid=KVR52U42BS8-16) · [Micron 1Rx8 UDIMM 图及 PMIC/SPD](https://assets.micron.com/adobe/assets/urn%3Aaaid%3Aaem%3A5902f17e-8bde-4246-971c-8d7f274c6b1a/original/as/ddr5-key-module-features-wp-client.pdf)
- **阵列行为。** 逐级显示 `CPU 通道 → 模组子通道 → rank → bank group → bank → row/column → cell`。通用 1T1C 模型用一个访问晶体管和一个储存电容表示一位，字线选通，位线先预充。`ACT` 打开一整行，电容与位线共享少量电荷，感测放大器判定电平并沿位线恢复原来的电荷。`RD` 选取行缓冲区中的列后通过 DQ/DQS 突发输出，`WR` 以输入电平改写所选列。列访问可与内部恢复重叠，开启的行可接受后续列访问，`PRE` 在满足时序后关闭该行并重新预充。电容的电荷随时间泄漏，控制器定期发出 `REFab` 或 `REFsb` 所代表的刷新操作，由器件在内部恢复电荷。图中电压、阵列比例和物理地址落入哪个 bank 都只用于说明，实际 DDR5 命令间隔取决于配置和当前 bank 状态。[Micron DDR5 器件核心数据表，ACTIVATE、PRECHARGE、READ/WRITE 及 REFRESH 各节](https://www.avnet.com/wcm/connect/dacdfea7-999f-4ee0-b514-6f9e0bf68c6d/ddr5-sdram-core.pdf?MOD=AJPERES) · [Micron 感测与电荷恢复公开专利](https://patents.google.com/patent/US6549476B2/en) · [Micron DDR5 技术资料](https://www.micron.com/products/memory/dram-components/ddr5-sdram)

## Linux Host、地址与事务

**事件前提。** 使用支持并成功进入直接 I/O 的路径，缓冲区按页对齐，单条 4 KiB 读写，无额外 metadata。CPU 页表提供软件虚拟地址到主机物理地址的转换。I/O 队列与缓冲区位于系统内存，示例使用 BAR 门铃、常规主机内存 SQ/CQ，以及可选 MSI-X 或轮询。CMB、Doorbell Buffer 与多命令并发可在驱动源码中各自观察。`O_DIRECT` 绕开文件数据 page cache，CPU 缓存、虚拟内存及 DMA 映射继续工作。以 iomap 文件路径为例，`bio_iov_iter_get_pages()` 为 `bio` 获取应用缓冲区的页面，然后经 `request` 与 `blk-mq` 硬件派发队列进入 NVMe 驱动的 `nvme_queue_rq()`。设备完成后驱动解除负载的 DMA 映射，再经块层向软件报告结果。[Linux v6.12 iomap 直接 I/O](https://docs.kernel.org/6.12/filesystems/iomap/operations.html#direct-i-o) · [iomap 直接 I/O 取页与提交](https://github.com/torvalds/linux/blob/v6.12/fs/iomap/direct-io.c#L375-L439) · [Linux v6.12 blk-mq](https://docs.kernel.org/6.12/block/blk-mq.html) · [Linux v6.12 NVMe 提交与完成代码](https://github.com/torvalds/linux/blob/v6.12/drivers/nvme/host/pci.c#L840-L1128)

**地址和屏障。** 每块 SQ/CQ 在该路径由 `dma_alloc_coherent()` 分配。数据页经 streaming DMA API 映射，驱动把设备可见的 `dma_addr_t` 放入 PRP 或 SGL。若启用有地址转换的 IOMMU 域，PCIe 请求依设备身份和 I/O 页表把 IOVA 翻译到主机物理地址，并施加设备读写权限。直映或旁路的配置也可存在。MMIO 门铃地址来自 SSD 的 PCI BAR，经 `ioremap()` 后以 `writel()` 访问。DMA 一致性处理 CPU 与设备对内存内容的可见性，驱动还依靠访问顺序与屏障确保 SQE 在通知设备前发布、CQE 的 phase 在其余字段之前检查。MSI-X 在启用中断重映射的配置下可经 IOMMU 的中断重映射表处理。[Linux v6.12 DMA API](https://docs.kernel.org/6.12/core-api/dma-api-howto.html#cpu-and-dma-addresses) · [Linux IOMMU 权限映射](https://github.com/torvalds/linux/blob/v6.12/drivers/iommu/dma-iommu.c#L734-L760) · [Linux MMIO 文档](https://docs.kernel.org/6.12/driver-api/device-io.html) · [Linux v6.12 分配 SQ/CQ](https://github.com/torvalds/linux/blob/v6.12/drivers/nvme/host/pci.c#L1535-L1598) · [AMD IOMMU 规范 48882 §2.2.2.1](https://www.amd.com/content/dam/amd/en/documents/processor-tech-docs/specifications/48882_IOMMU.pdf)

| 可见事件 | 发起方、方向和结果 |
| --- | --- |
| 准备并提交 SQE | CPU 把命令和 PRP/SGL 写入主机 SQ，推进 SQ tail。示例显示 64 B SQE。CPU 用 `writel()` 更新 SSD BAR 内的 SQ Tail Doorbell，链路为主机 → SSD 的 posted `MWr`，内容是新指针。 |
| SSD 取 SQE | SSD 作 PCIe requester，向主机 SQ 发 non-posted `MRd`，host completer 用 `CplD` 返回命令字节。选用多页 PRP 列表或间接 SGL 时，也可能通过 `MRd` 获取描述符。 |
| NVMe Read | SSD 将读出的 4 KiB 通过 SSD → 主机的一个或多个 `MWr` 写进主机 DMA 缓冲区。Linux 方向是 `DMA_FROM_DEVICE`。 |
| NVMe Write | SSD 向主机 DMA 缓冲区发 `MRd`，主机用一个或多个 `CplD` 把负载返回 SSD。Linux 方向是 `DMA_TO_DEVICE`。 |
| 报告命令完成 | 数据传输完成后，SSD 再向主机 CQ 发布 CQE，示例显示 16 B 和独立的 posted `MWr`。首圈 phase 为 1，后续每次 CQ 环回翻转。启用 MSI-X 时，SSD 可另发一次目标为中断地址的 posted `MWr`。专用轮询队列从主机端检查 CQ，亦可批量收割已就绪的完成项。 |
| 消费并确认 CQE | CPU 用 `READ_ONCE` 比对 phase，`dma_rmb()` 后读取 CID、状态等字段。驱动推进 CQ head，以 CQ Head Doorbell 归还已消费的 CQ 槽，并依据 CID 完成块请求。请求回调与门铃的先后可随批处理和完成分派变化。 |

队列号为 `y` 时，SQ Tail 与 CQ Head 门铃相对 BAR 的偏移分别是 `0x1000 + 2*y*(4 << CAP.DSTRD)` 和 `0x1000 + (2*y+1)*(4 << CAP.DSTRD)`。SQ tail 由主机推进，CQ tail 由控制器维护。CQE 中的 `SQHD` 表示已消费到的 SQ 位置，状态和 `CID` 表示对应命令的完成结果。[NVMe over PCIe 1.0 §3.1.2](https://nvmexpress.org/wp-content/uploads/NVMe-over-PCIe-Transport-Specification-1_0-2021.06.02-Ratified-1.pdf#page=10) · [NVMe Base 2.0c §3.3.1.2、§3.3.3.2](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-2.0c-2022.10.04-Ratified.pdf)

事务方向依据 NVMe 的每个阶段和 PCIe 的 requester/completer 角色。正常 `MRd` 是带返回的请求，可对应多个 `CplD`。普通 `MWr` 是 posted 事务，PCIe 事务层对它无 `CplD`。PCIe 负载上限、读请求上限和边界共同约束拆包，表中 4 KiB 表示命令负载总量。数据 DMA、CQE、MSI-X 是不同目标的事务。动画按可观察的顺序展示单笔 I/O，实际命令可乱序完成，IRQ 也可能合并。Linux MSI 文档指出消息中断的写入在其相关数据写入之后交付，驱动仍检查 CQ 可见性。启用 volatile write cache 时，普通写成功可以早于最终介质持久化，FUA 或适用的 Flush 负责持久化语义。[NVMe over PCIe 1.0 §3.1.2、§3.4–3.5](https://nvmexpress.org/wp-content/uploads/NVMe-over-PCIe-Transport-Specification-1_0-2021.06.02-Ratified-1.pdf#page=10) · [NVMe Base 2.0c §3.3.3](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-2.0c-2022.10.04-Ratified.pdf#page=96) · [NVMe NVM Command Set 1.0c 的 Read、Write、Flush](https://nvmexpress.org/wp-content/uploads/NVM-Express-NVM-Command-Set-Specification-1.0c-2022.10.03-Ratified.pdf) · [AMD PCIe 事务与分包白皮书](https://docs.amd.com/api/khub/documents/4uw~7uS2eK5x7lKbNdxWlw/content) · [Linux MSI 文档](https://docs.kernel.org/6.12/PCI/msi-howto.html) · [Linux v6.12 DMA 方向宏](https://github.com/torvalds/linux/blob/v6.12/include/linux/blk-mq.h#L228-L231)

在 NVMe 控制器页大小为 4 KiB、PRP 模式且全段位于一个已映射页内的示例中，`PRP1` 指向负载起点。跨页时由 `PRP2` 指向下一页或 PRP 列表。用独立字段显示 NVMe 的页大小和 PCIe 的最大 TLP 负载。命令的 `NSID`、`SLBA`、`NLB` 指定存储范围，`NLB` 为零起算。4 KiB 对应一个 4 KiB LBA 或八个 512 B LBA，取决于命名空间格式。[NVMe Base 2.0c §3.3.3.1、§4.1.1](https://nvmexpress.org/wp-content/uploads/NVM-Express-Base-Specification-2.0c-2022.10.04-Ratified.pdf) · [NVM Command Set 1.0c 的 Read、Write 字段](https://nvmexpress.org/wp-content/uploads/NVM-Express-NVM-Command-Set-Specification-1.0c-2022.10.03-Ratified.pdf)

## 可复用的开源模型

- **Ramulator 2.1，MIT。** 源模型 `python/ramulator/dram/ddr5.py` 通用组织可直接取 `DDR5_16Gb_x8`，生成的 `src/ramulator/dram/impl/DDR5.cpp` 提供运行时模型。该预设为器件 ×8、模拟通道 ×32、每通道 1 rank、8 bank groups × 4 banks，每 bank `2^16` 行 × `2^10` 列。四个 ×32 模拟通道映射到 A2/B2 的四个子通道。`DDR5_5200B` 给出 CL/tRCD/tRP 42/42/42，`tCK_ps=384` 为模型的整数精度，`nBL=8` 是时钟周期数量，接口为 BL16。可复用命令状态与时序约束，也可用现成模拟器生成轨迹。SPD 以模组数据表为准，模拟器的二级时序、SMU/UMC 策略、地址映射和 1T1C 模拟各有模型边界。MIT 允许复用实现，随复制的代码保留上游版权及许可文本。[固定版本 DDR5 组织](https://github.com/CMU-SAFARI/ramulator2/blob/7bead6cb7c4b03e095c6d4769ae3181a8e0bf6da/python/ramulator/dram/ddr5.py#L440-L449) · [DDR5-5200 预设](https://github.com/CMU-SAFARI/ramulator2/blob/7bead6cb7c4b03e095c6d4769ae3181a8e0bf6da/python/ramulator/dram/ddr5.py#L550-L568) · [生成的 C++ 模型](https://github.com/CMU-SAFARI/ramulator2/blob/7bead6cb7c4b03e095c6d4769ae3181a8e0bf6da/src/ramulator/dram/impl/DDR5.cpp) · [MIT 许可证](https://github.com/CMU-SAFARI/ramulator2/blob/7bead6cb7c4b03e095c6d4769ae3181a8e0bf6da/LICENSE)
- **Linux v6.12 Host，GPL-2.0。** `nvme_queue_rq` / `nvme_sq_copy_cmd` / `nvme_write_sq_db` 提供提交，`nvme_pci_setup_prps` / `nvme_pci_setup_sgls` 提供数据指针，`nvme_cqe_pending` / `nvme_poll_cq` / `nvme_irq` 提供收割和 IRQ。可沿用内核现有 tracepoint 观察真实主机块请求和 NVMe 命令，把事件转换为动画输入。内核源文件另有自己的许可证要求。[Linux NVMe PCI 源码及 SPDX 标记](https://github.com/torvalds/linux/blob/v6.12/drivers/nvme/host/pci.c#L1) · [Linux NVMe tracepoint](https://github.com/torvalds/linux/blob/v6.12/drivers/nvme/host/trace.h) · [Linux COPYING](https://github.com/torvalds/linux/blob/v6.12/COPYING)
- **QEMU v9.2.0 NVMe 设备，GPLv2 或以后。** `hw/nvme/ctrl.c` 的 `nvme_process_db`、`nvme_process_sq`、`nvme_post_cqes`、`nvme_irq_assert` 可对应门铃、抓取、写回和通知。运行现成模拟器可通过 `pci_nvme_mmio_doorbell_sq`、`pci_nvme_io_cmd`、`pci_nvme_enqueue_req_completion`、`pci_nvme_mmio_doorbell_cq` 获取各关键点。轨迹观察的是虚拟控制器对队列和 guest DMA 的操作。Gen4 链路上的实际 TLP 拆包、计时、Samsung 固件内部调度与主板信号完整性需要自己的证据。[QEMU 模型及文件许可证](https://github.com/qemu/qemu/blob/v9.2.0/hw/nvme/ctrl.c#L1-L9) · [QEMU NVMe trace-events](https://github.com/qemu/qemu/blob/v9.2.0/hw/nvme/trace-events) · [QEMU tracing 文档](https://www.qemu.org/docs/master/devel/tracing.html)
